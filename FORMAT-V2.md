# Orbit64 V2 state token format

**Status: draft.** This document specifies the second Orbit64 state format. It
is not a revision of [FORMAT.md](FORMAT.md): V2 drops V1's class bits and
replaces them with a registry of puzzle types, so the two formats are separate.
Nothing here changes what V1 tokens mean. The reference implementation is
`Orbit64.V2` (`src/Orbit64/V2/`), checked against the reference vectors in
`test/TestV2VectorData.flix`, which an independent Julia encoder
(`tools/format-v2/vectors.jl`) generates from this text alone.

The state counts and parity relations the format relies on are checked by
[`tools/format-v2/proof_obligations.jl`](tools/format-v2/proof_obligations.jl),
and its committed output is
[`tools/format-v2/proof-obligations.md`](tools/format-v2/proof-obligations.md).
[Proof obligations](#proof-obligations) says which steps that program checks
and which rest on short arguments given here. The slot tables are in
[`FORMAT-V2-SLOTS.md`](FORMAT-V2-SLOTS.md), generated by
[`tools/format-v2/slots.jl`](tools/format-v2/slots.jl).

## Goals

1. **Short tokens for small puzzles.** The target is the information-theoretic
   minimum, `ceil(bits / 6)` characters. Every entry of the initial registry
   meets it. The allocation rule does not guarantee it for later entries: a
   later entry can land one length further. Beyond about 20 characters, one
   character more or less matters little.
2. **No wasted values.** Nothing in V2 is a bit field. Every piece of
   information is a mixed-radix digit with exactly as many values as it has
   possibilities, and parity-coupled information is not stored at all.
3. **Self-identifying.** A token alone names its puzzle type and its state.
   No side channel is needed beyond knowing that it is a V2 state token.
4. **Readable solved states.** A solved puzzle of a type that starts its
   length is `A` repeated to that length.
5. **Long-lived.** The token rules in this document are meant to stay frozen.
   New puzzle types are added through the registry. Adding one never changes
   the meaning of an existing token.

## Token text and value

A token is a string of length `L >= 1` over the base64url alphabet, without
padding, in this index order:

```text
ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789-_
```

Its **value** `V` is the string read as a big-endian base-64 numeral, so
`0 <= V < 64^L`. Leading `A` characters are significant. A token's length is
part of the token. `A` and `AA` are different tokens, and every string of
length `L` is a distinct token.

## Registry and allocation

The **registry** is an ordered list of entries. Entry `i` has the ID `i` and
describes one puzzle type. It specifies:

- a **state count** `N_i`, an exact positive integer;
- a **rank function**, a bijection from the type's states onto `[0, N_i)`
  that ranks the type's distinguished zero state, normally the solved state,
  as `0`.

**Allocation rule.** The entries are placed in registry order. Entry `i` takes
the shortest length whose unallocated values can still hold all its states,
and starts its range directly after the entries already placed at that length:

```text
used(L)  = sum of N_j over the entries j < i with L_j = L    (0 if there are none)
L_i      = the least L >= 1 with used(L) + N_i <= 64^L
offset_i = used(L_i)
```

A state of entry `i` with rank `r` is the token of length `L_i` whose value is
`offset_i + r`.

**Decoding.** Given a token of length `L` and value `V`, find the entry with
`L_i = L` and `offset_i <= V < offset_i + N_i`. Its rank is `V - offset_i`.
If no entry matches, the token is rejected: it is malformed, or it belongs to
an entry added by a newer registry. A decoder should report the two cases the
same way, for example as "not a known V2 state token".

**Growth rules.** These rules make adding an entry safe:

- Entries are only appended. An entry is never removed, reordered, or changed,
  and its ID is never reused. A retired type keeps its range.
- Appending entry `i` changes no earlier entry's length or offset, because the
  rule places `i` from what earlier entries left. So no existing token ever
  changes meaning.
- The first entry placed at a length has offset `0`, so its zero state is
  `A` repeated `L` times. Any other entry's zero state is the length-`L_i`
  token whose value is `offset_i`.

The registry is part of this specification. Implementations may compute the
lengths and offsets with the rule or hard-code the table below. Both give the
same result.

## The n x n x n cube types

Entries 0 to 53 are members of one family: the `n x n x n` cube for
`n = 2..15`, in two **sticker models** and two **pose variants**. A 2x2x2 has
no centers, so its picture model equals its color model. There is no 2x2x2
picture entry: a picture-model 2x2x2 is written as entry 0 or 1.

### Pieces and orbits

A cube with `m = n - 1` has these cubie orbits. Moves permute pieces only
within an orbit.

| Orbit | Pieces | Exists when | Orientation |
| ----- | -----: | ----------- | ----------- |
| corners `C` | 8 | always | twist in `0..2` |
| midges `M` | 12 | `n` odd | flip in `0..1` |
| wings `W1..Ww` | 24 each | `w = floor((n - 2) / 2)` orbits | fixed by position |
| centers `Z` | 24 each | `floor((n - 2)^2 / 4)` orbits | fixed by position |
| fixed centers | 6 | `n` odd | rotation in `0..3` |

Wing orbit `Wd` holds the wings at depth `d`, so `W1` is the outermost.

**Center orbits.** The center cells of a face are `(row, col)` with
`1 <= row, col <= n - 2`, counted from 0. The orbit `Z[r,c]` is the orbit of
the `U`-face center cell `(r, c)` under the 90-degree rotation
`(r, c) -> (c, n - 1 - r)`, so it holds the four rotated cells on each of the
six faces, 24 facelets. Its representative `(r, c)` is the cell with the
lowest facelet index, `r * n + c`, among the four. The fixed center of an odd
cube is not in an orbit. The orbits are listed by `r = 1..n-2` ascending, and
for each `r` by `c = r, r + 1, ...` while `c < n - 1 - r`. There are
`floor((n - 2)^2 / 4)` of them. This is the order of the center digits. For
`n = 7`: `Z[1,1], Z[1,2], Z[1,3], Z[1,4], Z[2,2], Z[2,3]`.

A wing or center piece has no orientation of its own. A cubie's orientation is
the rotation that takes it from its home position to its current one. For a
cubie that no nontrivial cube rotation keeps in place, which is every wing and
every non-fixed center, that rotation is determined by the position alone.
Only corners (3 orientations), midges (2) and fixed centers (4) have a point
stabilizer.

### Sticker models

- **Color.** Stickers carry one of six colors. Corners, midges and wings are
  still distinguishable by their colors. The four centers of one color in a
  center orbit are not, and a fixed center's rotation is invisible. A center
  orbit is therefore a multiset with four copies of each color, and fixed
  centers carry no rotation.
- **Picture.** Every sticker is distinguishable and its rotation is visible.
  Center pieces are numbered by their home slot, and each fixed center records
  its rotation.

The picture model covers any cube whose stickers all differ, such as labeled,
printed or photo cubes. A cube with only some distinguishable stickers is a
future registry entry, see [Extensions](#extensions).

### Pose variants

- **Canonical.** The whole-cube orientation is not part of the state. On odd
  cubes the state is read after turning the cube so that the six fixed centers
  are home: by color in the color model, by piece in the picture model. On
  even cubes it is read after turning the cube so that the DBL corner is in
  slot DBL with twist 0. Exactly one of the 24 rotations does this, see
  obligation P3.
- **Framed.** The whole-cube orientation is part of the state, and the token
  carries 24 times as many states. On odd cubes the frame is stored as a final
  digit. On even cubes it is carried by all eight corners, as in V1.

Canonical is the default. Use framed only when the use case needs the cube's
orientation in space, for example a display or a camera-relative scan.
Converting framed to canonical is total and loses only the frame. Converting
canonical to framed sets the frame rank to `0` on odd cubes. On even cubes the
canonical state, with DBL home, is itself the framed state.

### Conventions

V2 uses V1's slot convention `orbit64-Nxn-draft@1` unchanged: the corner and
midge slot orders, the twist and flip conventions, and the wing and center slot
tables. [FORMAT-V2-SLOTS.md](FORMAT-V2-SLOTS.md) lists the facelet index of
every slot of every orbit for `n = 2..15`, and is normative for the slot
tables. The program that generates it is
[`tools/format-v2/slots.jl`](tools/format-v2/slots.jl).

For `n >= 8` the tables extend V1's rule for the 6x6x6 and 7x7x7. Take the
4x4x4 (`b = 4`, even `n`) or 5x5x5 (`b = 5`, odd `n`) reference slots. For a
reference facelet `face * b^2 + row * b + col`, keep the face and replace each
axis coordinate: `0` stays `0`, `1` becomes `d`, `2` becomes `floor(n / 2)` when
`b = 5`, `b - 2` becomes `n - 1 - d`, and `b - 1` becomes `n - 1`. Corners and
midges use `d = 1`, and wing orbit `Wd` uses its depth `d`, for `d = 1..w`.
The 24 slots of each center orbit are ordered by facelet index. In V2, the
names `orbit64-8x8-draft@1` to `orbit64-15x15-draft@1` mean exactly this
extension, although V1's `Net.convention(n)` names no convention above 7.

The solved state of a color-model center orbit has its colors ascending by
slot: slot `i` has color `floor(i / 4)`. This is why the all-zero multiset
rank is the solved state. A picture-model orbit is solved at the identity
permutation.

The six colors are the face indexes `U R F D L B` = `0..5`. Frames use V1's
`Frame` order of the 24 right-handed whole-cube frames. A piece is numbered by
its home slot, so the solved state is the identity.

The new conventions for the picture model are:

- **Center identity.** The piece whose home is slot `j` of an orbit is piece
  `j`. An orbit's state is the permutation `p`, where `p[i]` is the piece in
  slot `i`.
- **Fixed-center rotation.** Each face's reference direction points toward
  row 0 of that face in FORMAT.md's facelet geometry: toward `B` on `U`,
  toward `F` on `D`, and up on the four side faces. A fixed center's rotation
  `r_f` is the number of clockwise quarter turns, seen from outside, that take
  face `f`'s reference direction to the piece's own reference direction (the
  direction that pointed to row 0 when the cube was solved).

### Rank primitives

`par(p)` is the parity of permutation `p`: 0 if even, 1 if odd. The
primitives are V1's, defined in `Orbit64.Rank`:

- **Permutation rank** of `p` over `0..k-1`:
  `sum_{i=0}^{k-1} c_i * (k - 1 - i)!`, where
  `c_i = #{ j > i : p[j] < p[i] }`. Radix `k!`.
- **Parity-reduced rank** of `p` with known parity: the same sum over
  `i = 0..k-3` only, with each term divided by 2. The order of the last two
  entries follows from the parity. Radix `k!/2`. Each term
  `c_i * (k - 1 - i)! / 2` is an integer, and the sum is exactly the Horner
  rank of the first `k - 2` Lehmer digits `c_0, ..., c_{k-3}` with radices
  `k, k - 1, ..., 3`. Only the midge permutation and the picture-model center
  orbits use it. Corner permutations never do: their parity is free in every
  type. Odd cubes and even framed cubes rank all eight corners in full, radix
  `8!`, and even canonical cubes rank seven, radix `7!`.
- **Multiset rank** of a 24-slot center orbit with four copies of each color:
  for colors `t = 0..4` in turn, take the slots still unassigned, numbered
  `0, 1, ...` in ascending slot order, and rank the positions of color `t`
  among them by the combinatorial number system, `sum_i C(s_i, i + 1)` over
  the ascending positions `s_0 < s_1 < s_2 < s_3`. Combine these with
  radixes `C(24, 4), C(20, 4), C(16, 4), C(12, 4), C(8, 4)`, most significant
  first. Color 5 fills the rest. Radix `24! / (4!)^6`.
- **Orientation digits**: the first `k - 1` orientations in slot order, read
  little-endian, so the first slot is the units digit. The last orientation
  follows from the orientation law.

### Digit layout

A state's rank is the Horner combination of these digits, most significant
first. Digits that do not exist for a size or model are skipped.

| # | Digit | Radix |
| -: | ----- | ----: |
| 1 | corner permutation, permutation rank | `8!`, or `7!` (even, canonical) |
| 2 | corner twists, orientation digits | `3^7`, or `3^6` (even, canonical) |
| 3 | midge permutation, parity-reduced rank | `12!/2` |
| 4 | midge flips, orientation digits | `2^11` |
| 5 | each wing orbit `W1..Ww`, permutation rank | `24!` |
| 6 | each center orbit, in orbit order: multiset rank (color) or parity-reduced rank (picture) | `24!/(4!)^6` or `24!/2` |
| 7 | fixed-center rotations (picture, odd) | `2^11` |
| 8 | frame (framed, odd) | `24` |

**Even canonical corners.** The DBL corner (slot and piece 6) is home with
twist 0 and is left out. The stored slots are 0..5 and 7, in that order, at
stored positions 0..6, so the DRB slot (7) is stored at position 6. A stored
piece `s` is renumbered `s - [s > 6]`, so the DRB piece also becomes 6. Twists
keep V1's per-slot values, with slot 7's twist stored at position 6. Digit 2
holds the twists at positions 0..5, and the one at position 6 follows from the
twist law, since DBL's twist is 0. In the even framed variant, all eight
corners are stored as in V1. The cube's orientation is then implicit in them,
so there is no frame digit.

**Pose.** The caller normalizes the pose before ranking, and the rank
function sees only the normalized state. On odd cubes the positions of the fixed
centers are implicit (they are home); only their rotations are stored, in the
picture model (digit 7, below). The frame is the last digit
(digit 8), the least significant one, and it must be `0` unless the type is
odd and framed. On even cubes DBL is home in the canonical variant, and the
frame is always `0`, since there is no frame digit.

**Fixed-center rotations.** Digit 7 combines the six rotations:
`r_U + 4 r_R + 16 r_F + 64 r_D + 256 r_L + 1024 * floor(r_B / 2)`. The parity
of `r_B` follows from the relation `R = C` below, where
`R = r_U + r_R + r_F + r_D + r_L + r_B`.

### Parity relations

Reachable states satisfy the orientation laws (corner twists sum to 0 mod 3,
midge flips to 0 mod 2) and these parity relations, mod 2. Here `C`, `M`,
`Wd` and `Z[r,c]` stand for the permutation parities of those orbits, and `R`
for the parity of the total fixed-center rotation.

**Picture model.**

- `M = C` and `R = C` (odd cubes);
- for every center orbit `Z[r,c]`, with `d = min(c, n - 1 - c)`:

  ```text
  Z[r,c] = C + Wr + Wd
  ```

  where a term `Wk` is absent when the cube has no wing orbit at depth `k`.
  That is the middle depth of an odd cube, so a `+`-center orbit gives
  `Z[r,c] = C + Wr`. An X-center orbit (`r = d`) gives `Z[r,c] = C`, because
  the two equal terms cancel.

**Color model.** `M = C` on odd cubes, and nothing else.

These are all the relations (obligation P2), and they hold in both pose
variants. On even cubes, `C` is the parity of all eight corners, which equals
the parity of the seven stored ones when DBL is home. A center orbit `Z` is a
picture-model **forced** component, stored with the parity-reduced rank. So is
`M`. For `R`, the low bit of `r_B` is not stored. A decoder computes the
forced parities from the free ones on the right. Corners, wings and the color
model's center multisets are never forced.

For example, the 7x7x7 picture model has `M = C`, `R = C`, `Z[1,1] = C`,
`Z[1,2] = C + W1 + W2`, `Z[1,3] = C + W1`, `Z[1,4] = C + W1 + W2`,
`Z[2,2] = C` and `Z[2,3] = C + W2`. The proof report lists the relations for
every size as computed.

### Encoding and decoding

To **encode** a state of entry `i`:

1. For a canonical entry, normalize the pose. For a framed odd entry, record
   the frame and normalize.
2. Validate. An invalid state is an error, never a token and never a crash.
   Validation has two stages, in this order, because the laws index into the
   components and are only defined once the layout is sound.
   - **Layout** (shape and ranges). Components the type lacks are empty and
     the others have the right number of entries; every permutation is a
     permutation of its orbit; twists are in `0..2`, flips in `0..1`,
     rotations in `0..3`, the frame is in `0..23` (and `0` unless the type is
     odd and framed) and colors are in `0..5`; each color multiset has four
     of each color.
   - **Laws.** A canonical even state has DBL in slot DBL with twist 0, the
     orientation laws hold, and the parity relations hold. (The positions of the
     fixed centers of an odd cube are implicit, see Pose; their rotations are
     digit 7, picture model only.)
3. Compute the digits, combine them, add `offset_i`, and write the result at
   length `L_i`.

To **decode**, find the entry and its rank (see
[Registry and allocation](#registry-and-allocation)). Split the rank into its
digits from the least significant end. Unrank the free components, compute the
forced parities, then unrank the forced components and complete the
orientations. Every rank below `N_i` decodes to a valid state, and every valid
state encodes to exactly one rank.

## Proof obligations

Each claim the format relies on is listed here, with how it is established.
"Checked" means that `proof_obligations.jl` computes it with exact integer
arithmetic and stops with an error if it fails. The script needs only Julia's
standard library and checks `n = 2..15` in about a minute.

- **P1. Ranks are bijections.** *Argument.* Each digit is a bijection onto its
  radix: Lehmer codes, the combinatorial number system, positional orientation
  digits, and the parity-reduced rank for a fixed parity. A mixed-radix Horner
  combination of bijections is a bijection onto the product of the radixes.
  This product equals `N_i` by P2.
- **P2. The counts and relations are exact.** Let `H` be the group of reachable
  states with the reference home, generated by every layer turn except the
  middle layers (odd) or the three layers holding DBL (even). The script
  establishes `lower <= |H| <= upper` with `lower = upper`:
  - **Upper bound.** Every reachable state satisfies:
    - the twist and flip laws. *Checked* on every generator. That this
      suffices is an *argument*: the twist and flip of a piece are measured
      against fixed per-slot reference facelets, so they add up under
      composition.
    - the per-piece orientation counts. *Checked*: for one piece of each orbit,
      the orbit of its (facelet, tangent) points under the generators of `H`
      reaches every slot and has exactly `slots x orientations` elements.
      Over the slots, a group orbit's fibers all have the same size, so each
      slot allows exactly that many orientations. The stabilizer argument
      under [Pieces and orbits](#pieces-and-orbits) explains why.
    - the parity relations. *Checked*: they are the GF(2) linear forms that
      vanish on every generator of the full group, restricted to fixed centers
      at home. Parity is a homomorphism, so each form vanishes on the whole
      group. Each relation halves the count.

    The script also *checks* that these relations equal the closed form above
    for every `n = 2..15`.
  - **Lower bound.** *Checked*: the product of the orbit lengths of a
    Schreier-Sims chain built from elements of `H`. Every element in the chain
    lies in `H`, so the product never overstates `|H|`. Random elements only
    decide how fast the bound grows, never whether it holds.
  - **Color model.** *Argument*, using `|H| = upper`, which says that every
    picture state satisfying the relations is reachable. The color model's
    states are the picture states with center identities and rotations
    forgotten. Two same-colored centers of one orbit can always be swapped,
    and a fixed center can always be turned, without changing the colors. So
    the color relations are exactly the picture relations that involve no
    center and no `R`. The script *checks* that
    `24 * N(color canonical) = V1 State.stateCount(n)` for every `n`.
- **P3. The pose normalization is well defined.** *Argument.* The reference
  has exactly 24 poses: fixed centers on odd cubes, DBL with its twist on even
  cubes. On odd cubes moves move fixed centers only rigidly, as a rotation. On
  even cubes a corner has `8 * 3 = 24` poses. The 24 whole-cube rotations reach
  all of them, and only the identity keeps the reference home. So every state
  has exactly one canonical form, and framed counts are 24 times canonical
  counts.
- **P4. Ranges are disjoint and stable.** *Argument*, from the allocation rule;
  see the growth rules.
- **P5. Lengths and offsets are exact.** *Checked* with exact integers. The
  fullest length is 42, at 97.72% after entry 11.
- **P6. Solved is the zero state.** *Argument.* The solved state has identity
  permutations, zero orientations and frame rank 0, so every digit is 0 and
  its rank is 0. Its token is `A` repeated `L_i` when `offset_i = 0`.

Every future entry must come with the same obligations: an exact count with a
proof, a bijective rank with zero for its zero state, and reference vectors.

## Relation to V1

V2 drops V1's class bits. It also drops V1's move-sequence and
structured-algorithm classes and the extension envelope from the state token
space. Those formats are not state tokens, and a V2 token is only a state
token. V1's canonical form, the pattern class under rotation, mirror and
recoloring, is a separate function and not a V2 pose variant.

**V1 tokens read by V2.** The digit layouts of the color framed entries are
V1's coordinate order. In the initial registry, entries 1, 3, 7, 15 and 19
start at offset 0 at V1's token widths 5, 12, 27, 66 and 90. A V1 state token
for the 2x2x2, 3x3x3, 4x4x4, 6x6x6 or 7x7x7 is therefore the V2 token of the
same state. A V1 5x5x5 token has 43 characters, a length where the initial
registry has no entries, so a V2 decoder rejects it rather than misreading it.
This is a property of the initial registry, not a promise.

**V2 tokens read by V1.** This direction is unsafe. A V2 token has no class
bits, so a V1 decoder can take it for a move sequence or an algorithm. For
example, an 11-character 3x3x3 canonical token can start with `Q` to `f`,
which is V1's move-sequence class. Wherever a V1 decoder might see V2 tokens,
V2 tokens MUST be labeled, for example by a field name or an `orbit64v2:`
prefix.

## Extensions

New types are appended to the registry. Directions already anticipated:

- **Larger cubes** (`n > 15`) and **cuboids** `a x b x c`, appended member by
  member when needed. A family is a naming convention, not a token feature.
- **Unconstrained variants**: physically assembled states that ignore the
  orientation laws and parity relations. A scanner needs them to report a
  misassembled cube, and the count is the product of the free radixes.
- **Partial distinguishability**: cubes where only some stickers differ, for
  example a logo on one center. Such an entry declares which pieces are
  equivalent. The color and picture models are the two extremes.
- **Masks**: states with unknown pieces, for partial scans and learning goals
  such as "only the cross matters".
- **Other puzzles and shape changers**: pyramids, megaminxes, Square-1,
  bandaged cubes. Each needs its own rank function and count proof.

Symmetries of a sticker's design, such as a `0` that looks the same after a
half turn, belong in a goal or target definition, not in the token. The token
records the physical state.
